# WP8 S3g2b — credential lifecycle and protected-storage boundary

This increment provides the private role-specific credential record, explicit local maintenance gate, high-entropy material generation/import, revoke-before-replace and an opt-in dedicated encrypted NVS backend. It does not provide a customer pairing screen, a secure transfer channel, factory station, partition layout, actual encryption key provisioning, ESP compilation or production activation. No existing Browser, racing, storage, SDK, flash or device entry points change.

## Historical customer workflow proposal — superseded

**Superseded by the [owner's automatic-connection decision](https://github.com/ConnalM/Plonk-and-Play/issues/14#issuecomment-7143384071) and the design specification.** Retained below as historical rationale, not a current requirement. No customer code, pairing button or service equipment is required. The automatic first-use bootstrap and replacement mechanism must be designed separately; the tested vault is not itself an automatic commissioning protocol.

The preferred out-of-box experience is a factory-matched optional Taster and Core, with a different random 128-bit PairId and 256-bit PSK for every matched pair. Core-only customers have no Taster credential. Neither normal startup nor reconnect needs customer intervention. Pairing is independent of Wi-Fi association; a public SSID, MAC, IP address or short PIN must never become a shared secret. A Taster cannot join the race-control link merely by seeing the Core's AP.

For a replacement, the proposed service workflow is a deliberate local maintenance action on Core (possible physical button/service connection, subject to board and UX approval), only when READY with no active race, with all Taster transport references destroyed before changing credentials. Verify durable Core revocation first, then use fresh random material on the new Taster and Core through a trusted confidential and authenticated out-of-band provisioning channel. The customer must be shown an explicit completion/verification result only after the new mutually authenticated connection works. Old Taster remains unable to authenticate after verified revocation and installation of fresh material, whether it is lost or still powered. If interrupted after revocation, Core can still operate through SMUGLAND; finish commissioning locally, never auto-reinstate the old key. Core-only, paired/replacement Taster, lost Taster and interrupted service scenarios must be designed and reviewed before release. Actual customer method (physical service connection, approved local UI and secure transfer protocol) is a separate design decision. No remote pairing endpoint, plaintext code entry, secret display, default PSK, automatic pairing mode or credential export is implemented here.

## Record and authority

One canonical 64-byte big-endian PPCR v1 record in a private role-specific store: magic, version, Core/Taster role, paired flag, reserved zero, nonzero local 32-bit revision, 16-byte PairId and 32-byte PSK (both zero for revoked), CRC32 for accidental corruption. CRC is not cryptographic authenticity, a key verifier or rollback protection. PairId/PSK match across devices; role and revision are local. A new install requires empty/revoked state, explicit fresh candidate from trusted provisioner, expected local revision, physical/service authorisation, safe lifecycle and destroyed/quiescent transport. Existing pair must be durably revoked before installation. Local revision never wraps; reserve final revision for revocation. Trusted provisioner must generate independent new pair material on replacement; this record does not maintain a blacklist or prove imported material's entropy/freshness. A trusted operator that deliberately reinstalls old material would defeat revocation.

Vault loads once before constructing transport, distinguishes missing/empty from corrupt/unavailable/wrong-role/fault, and exposes only a read-only credential reference while paired. Credential memory is noncopyable at the object level, cleared through provider wipe at destruction/failure/replacement; scratch records and temporary decoded keys are wiped. Material import source is the trusted provisioner's responsibility to wipe. Authority checks are synchronous owner-supplied trusted facts, not values parsed from a network message or unauthenticated UI. Maintenance and transport must be mutually exclusive on the same owner, including lifetime of all borrowed references. Factory reset of ordinary presentation/race settings must not touch pairing. No logging, diagnostics dumps, SD, shared slot allocation or Browser API.

## Durability and uncertainty

Backend contract is exclusive protected storage, one atomic durable blob replacement on success and exact readback before reporting Applied. No previous-slot fallback or automatic erase/default. A storage fault latches Fault for the current instance and clears RAM credential availability, preventing local service startup until authorised recovery. Verified revocation commits a zero-material tombstone before any new installation. If failure/power loss precedes verified revocation, an old valid record may survive reboot; do not report old Taster revoked. Physical recovery must re-establish the committed state with transport disabled before declaring revocation complete; automatic reboot must not be advertised as a repair or proof of revocation. If installation fails after verified revocation, ordinary atomic old/new recovery yields revoked or new pair, never the old paired record. A reboot after failed write has uncertain committed state until read/verified. Cross-device provisioning is not a distributed atomic transaction; explicit completion is necessary. No anti-rollback or physical extraction guarantee; flash image rollback, malicious firmware and debug access require separate product security decisions. Tombstone is logical revocation, not guaranteed forensic erasure of flash.

ESP source adapter requests secure init of dedicated pp_pair NVS partition, using owner-provided approved security config. No default NVS, no erase, no automatic key generation, no partition changes, no fallback to plaintext. Exclusive startup must guarantee partition is not already initialised unencrypted and that device-specific encryption keys are protected. Caller owns and wipes nvs_sec_cfg_t; the adapter cannot certify eFuse/key protection, encrypted partition configuration, debug policy or production provisioning merely by accepting an approval bool. Use one NVS blob, nvs_set_blob then nvs_commit, close and fresh readback; no writes in sporting loop. Vendor reference: [ESP-IDF 5.5 NVS storage and secure partition init](https://docs.espressif.com/projects/esp-idf/en/release-v5.5/esp32s3/api-reference/storage/nvs_flash.html). Actual ESP compile and power-interruption testing required; no changes to partition/eFuse configuration here.
