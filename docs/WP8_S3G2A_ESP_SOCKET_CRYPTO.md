# WP8 S3g2a — opt-in ESP socket and crypto adapter source

S3g2a provides concrete BSD/lwIP socket owners and the ESP crypto/clock provider for the merged S3g1 Peer. It does not activate these objects in either firmware role, choose the Core board, install pairing material, change an SDK configuration, compile an ESP firmware image, or claim hardware acceptance. Existing integrated firmware and Browser paths remain unchanged.

## Socket ownership, network and capacity

The same socket runtime header is exercised with Linux TCP and selects lwIP headers under ESP_PLATFORM. The owner passes a coherent network generation and explicit local/Core IPv4 addresses in network byte order, after real network events have been marshalled to that owner. Core binds specifically to its AP IP, Taster binds its selected STA source IP and connects to the numeric Core IP. No wildcard binding, DNS discovery, external STA fallback or assumption that an SSID authenticates the peer. Binding a local address is not proof of interface-level isolation; production network routing/isolation remains to be verified. If the network epoch changes even with the same address, retire the old socket/peer. The external platform owner is responsible for actual AP/STA association, trusted selection of paired network, and stable entropy availability. No changes to the existing AP/STA manager in this increment.

One listener, one admitted peer including handshake, and a transient descriptor to refuse another accepted connection. Accept at most once per 100 ms, no backlog drain, no replacement or eviction by an incoming socket. Socket errors must not evict a healthy admitted peer. Peer I/O is nonblocking and bounded by S3g1. Taster starts a nonblocking connect, polls with zero-timeout select and verifies SO_ERROR, times out after 2 s, and backs off 0.5/1/2/4/8 s; only fresh authenticated display clears backoff. Association flaps retire the attempt but do not reset the backoff. No connection attempts while uncommissioned or network not ready. No sporting retry. Clock regression permanently disables the affected service instance. Existing race work must be serviced before Core poll, and Taster poll before renderer touch. ESP socket API semantics and TCP/IP-task latency still need actual compile and target evidence; one syscall is not a guarantee of execution duration.

Budget requires explicit commissioning and resource approval, reserve at least the existing ten Browser-related descriptors, and at least three additional slots for listener/peer/transient accept. Caller may reserve more for other services. On ESP the caller cannot overstate the total beyond CONFIG_LWIP_MAX_SOCKETS. The existing XIP sdkconfig has ten and therefore cannot activate this listener; even twelve would not meet the transient-accept allowance. Thirteen is a minimum for the presently audited Browser allowance, not a recommended final configuration. Actual coexistence, heap/PCB, stack and socket margin are required before capacity approval. No change to SDK config, HTTP connection limits or Browser service. Withdrawing approval closes the new transport only.

## Crypto and credentials

The audited XIP configuration has CONFIG_MBEDTLS_HKDF_C disabled. Instead of changing it, PPTH's fixed single SHA256 output block uses RFC5869 extract via HMAC(salt, PSK) and expand via HMAC(PRK, info || 0x01); only the existing 108-byte transcript salt and 32-byte output are supported, with bounded info. Both intermediate secrets are wiped on every completed path; HMAC errors wipe the output. This is not a general HKDF API. ESP provider uses mbedtls_md_hmac, mbedtls_ct_memcmp and mbedtls_platform_zeroize. The helper is compared with OpenSSL's independent HKDF for all five PPTH/PPTL domain labels and failure paths; ESP provider itself still requires target compilation.

EspCrypto requires an explicit entropy-ready callback controlled by the Wi-Fi lifecycle owner; no fallback to time, MAC address or unseeded PRNG. ESP-IDF documents that RF entropy is available when Wi-Fi/Bluetooth is enabled, not simply because Wi-Fi configuration exists. The owner must keep entropy available throughout the random call. Boot epoch is a nonzero 64-bit cryptographically random value generated once per boot with this provider; probabilistic uniqueness, not a persisted counter. Keep LinkIds for the entire Core boot, not each listener start or network event. No default PSK, no logging/export of keys, no automatically trusting a new device. Both services borrow securely loaded immutable pair ID and high-entropy PSK with a lifetime covering the service; commissioning, revocation, secure persistent storage/transfer, replacement procedure and encryption/threat-model decisions remain outstanding. Destroy/stop services before replacing material and wipe retired credentials at their owning storage boundary. Nothing writes NVS or SD here.

Reference platform API contracts: [ESP-IDF S3 RNG](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-reference/system/random.html), [ESP-IDF lwIP sockets](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-guides/lwip.html). These are API references, not evidence that the product build works.

## Host acceptance and remaining scope

The focused Linux test uses the actual socket owner header, TCP loopback and OpenSSL HMAC with the same PPTH KDF helper. A small CorePort fixture isolates network lifecycle tests; the separate S3g1 cumulative test exercises real Race Control and Noticeboard. Test budget floor/refusal, explicit authorisation, refused connect/backoff, real authenticated socket setup, extra peer refusal, command routing, same-address network epoch rollover, capacity withdrawal, AP loss, no offline retry, new authenticated session without replay, and clock regression. Compare HKDF with OpenSSL, inject each HMAC failure and entropy failure/zero epoch. Deterministic clock and loopback are not latency or wireless measurements.

Remaining S3g2 integration: actual Core AP and Taster STA lifecycle owners, secure commissioning and storage decisions/implementation, one boot-scoped allocator and provider activation, role-specific owner-loop wiring, committed preference revision and remote renderer/touch bridge. Select Core hardware and appropriate generated SDK socket/heap configuration without reducing SMUGLAND capacity. Separate target builds and physical two-device tests remain mandatory. This PR leaves all of those boundaries open.
