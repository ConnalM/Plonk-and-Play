# WP8 S3g2e — automatic first-use credential exchange

Bounded source/host increment implementing the first-use application exchange over a standard encrypted TLS channel. Consistent with the [owner-approved connection experience](https://github.com/ConnalM/Plonk-and-Play/issues/14#issuecomment-7143384071): no codes, passwords, pairing buttons, router, computer or internet. Does not activate a TLS listener, compile ESP TLS, provision secure storage, implement renderer/association owners or alter existing firmware paths.

## Threat model and eligibility

The approved customer experience has no external trust anchor for a previously unknown Core. Use a fresh standard TLS session (TLS 1.3 or TLS 1.2 ECDHE with AEAD; no early data, resumption, renegotiation or plaintext fallback) for initial confidential transfer, not a new custom cryptographic primitive. A self-signed certificate without prior verification demonstrates possession of its private key, not the product's identity. A malicious AP or active first-use man-in-the-middle can impersonate either endpoint or intercept/replace credentials. Passive observation of the Wi-Fi/TCP exchange must not reveal the PSK. Neither SSID, BSSID, device address nor PairId proves identity. This limitation is intrinsic to unauthenticated first use and must not be marketed as verified first-use identity. Factory pre-provisioning with matching vault and locator is possible separately, not required for the approved normal experience.

Core may admit only one exclusive bootstrap candidate when its vault is genuinely Empty, Core is READY/no active race, no sporting peer/credential borrower exists and the ordinary owner permits maintenance. Taster must be unremembered/Empty with the currently selected live association, no sporting peer or other credential borrower. Existing Paired, Revoked, Fault and Unloaded vaults cannot be entered automatically. Admission is an owner-controlled reservation revalidated throughout the exchange and at the existing vault mutation boundary; after local commit it continues only for that same reserved attempt, not another candidate. There is no automatic revocation/replacement, even if an old Taster is disconnected. A rogue first-use client could claim an empty Core; no claim of resistance to that without a trust anchor. The product's explicit replacement/admission/recovery policy remains open. Existing sporting authority, safety fences and nonofficial/record rules are untouched.

A future platform owner should use the same dedicated listener budget sequentially: empty Core accepts bootstrap TLS only, paired Core accepts ordinary PPTH only. No simultaneous secondary listener, no additional service carved out of SMUGLAND's capacity; actual accept/reject, mode switch, TLS negotiation/scheduling, storage latency, heap/stack/socket/PCB budget and Browser coexistence require implementation and measurement. Reserve the candidate before TLS negotiation, bound negotiation separately and retire it on readiness loss; never let TLS or NVS block an active race. No TLS work on the existing HTTP listener. Neither bootstrap nor a TLS channel grants race commands.

## Fixed exchange over TLS

One application exchange per fresh exclusive TLS connection. Fixed PPBS v1 header (magic/version/kind), no caller-controlled lengths. Request (6 bytes), Offer (54 bytes: fresh random 128-bit PairId and 256-bit PSK), Stored (22 bytes: same PairId), Done (22 bytes: same PairId). Secret is generated by Core CSPRNG and only sent inside TLS. No credential on raw TCP, in SSID, log, HTTP, SD or ordinary display. No default key or password derivation. TLS supplies application record confidentiality/integrity; no claim that PPBS itself authenticates an unknown endpoint. Header/order, exact PairId, role, original empty vault revision, committed material and admission are validated. Every mutation goes through existing Vault safe lifecycle, local authority, borrower quiescence, protected storage and verified readback. A future owner must explicitly implement these trusted policy facts; do not accept permission bits from a network packet.

Taster installs the offered material durably before sending Stored. Core installs the same material durably only after Stored matches. Core sends Done, closes the exchange; Taster verifies Done and closes. Both use new ordinary PPTH connection with committed vault material; only after PPTH authenticates and the selector verifies/persists the correct locator may normal control be enabled. Core sending Done is not proof of peer receipt. No TLS application frame is forwarded to Race Control, and there is no command path in this class.

At most one channel read OR write per poll, one application transition, fixed 54-byte buffer, no application backlog or retry of a write to persistent storage; partial I/O supported. Provisional 10 s exchange and 2 s per-record deadlines, monotonic regression fails closed. These cover application exchange, not actual TLS handshake or storage-call duration. The EncryptedChannel is a trusted platform abstraction for a fully negotiated fresh TLS session with bounded nonblocking I/O; passing arbitrary raw socket or pretending secure() is true violates its contract. Target adapter must enforce this before calling Exchange. Scratch frames, decoded material and generated credentials are wiped on finish/failure/destruction using the provider; TLS library buffers and device storage security depend on platform implementation.

## Interruption and subsequent connection

Distributed commit is not atomic. Complete is local exchange completion, not sporting readiness or guarantee the other side received the final message. Failed means no local mutation attempted; the other side may have committed. Uncertain means a local persistence attempt occurred and the exchange could not complete, even if a particular vault rejection was known not to write. No automatic rollback, revocation, fallback or replay after uncertainty. E.g. lost Stored can leave Taster paired/Core empty; lost Done can leave both paired; failed NVS writes retain the existing vault's documented readback uncertainty. Selector hint is still written only after actual PPTH. Power loss before that step may leave a paired Taster without matching locator; current selector fails closed, so production recovery must reconcile vault and locator safely without unnecessary customer intervention. Do not claim automatic interrupted first-use recovery or replacement is delivered here. In a healthy uninterrupted exchange both stores contain matching credentials; later PPTH requires possession, uses fresh sessions and preserves existing control fences.
