# WP8 S3g2f — Mbed TLS first-use channel

Opt-in shared Mbed TLS 3.6+ source adapter for the existing PPBS first-use exchange. Uses the SDK's Mbed TLS fork and existing lwIP nonblocking SocketStream on ESP; Linux exercises the same header against the distribution's upstream 3.6 library. Does not change active firmware, SDK/partition configuration, Core AP, SMUGLAND, physical devices or ordinary PPTH.

## Target configuration and policy

The checked-in WP7 XIP SDK configuration has TLS 1.2 client/server, ECDHE-ECDSA, ECP P-256 and GCM enabled; TLS 1.3 is disabled. Use precisely TLS 1.2 ECDHE-ECDSA AES-128-GCM SHA-256 (allowed by S3g2e), rather than enabling TLS 1.3 or additional sockets. Compile-time guard requires the actual library features including X.509 certificate writing; the checked-in config alone is not proof those macros or APIs are present in a generated production build. Mbed TLS 3.6 public API only. Verify generated configuration, SDK fork, security-patch status and vendor hardware crypto compatibility at target qualification. References: [Mbed TLS 3.6 API](https://mbed-tls.readthedocs.io/projects/api/en/v3.6.6/api/file/ssl_8h/), [ESP-IDF 5.5 Mbed TLS](https://docs.espressif.com/projects/esp-idf/en/release-v5.5/esp32s3/api-reference/protocols/mbedtls.html).

Create one new config/context per connection; no imported session, cache, server ticket callback, client tickets, renegotiation, session reset, early data or plaintext fallback. Check actual negotiated version/ciphersuite after handshake completion. Client deliberately has no independent CA/identity anchor on first use only; server has no previously known client identity. The Core generates a fresh P-256 key and self-signed X.509 certificate per attempt, signed SHA-256, using the provided CSPRNG. Fixed broad validity dates do not establish time or identity. No static shared private key, certificate file, internet time or new customer input. This is encrypted first contact with the previously approved active impersonation/rogue-first-client limitation; never apply verification-none to normal HTTPS or remembered PPTH. No new custom crypto. EspCrypto requires actual RF entropy throughout; initialise PSA before use if the actual library requires it. No keys logged, written to SD or persisted by this adapter.

## Owner and lifetime boundaries

MbedFirstUseChannel adopts one already-connected TCP socket, owns it even if start fails, and uses the existing SocketStream nonblocking socket and TCP_NODELAY helpers. No listener, reconnect or Wi-Fi manager is added. Owner must reserve exclusive genuine-empty first-use admission before connection/negotiation; verify selected live STA association, local AP/STA network address/generation, absence of sporting peer/credential borrowers, lifecycle/authority and resource approval; close on invalidation. Admission is checked before setup, before/after each handshake step, in BIO/RNG callbacks and on application operations; owner must maintain it across the same attempt after commit. This is not an admission implementation. Cannot attach to SMUGLAND, an active sporting peer or a listener. Never use a second listener; later owner selects bootstrap vs PPTH sequentially with the existing dedicated resource budget.

Fresh -> Negotiating -> Secure, or Closed/Fault terminal. A single mbedtls_ssl_handshake_step per poll, provisional 10-second monotonic deadline (includes setup by caller timestamp); WANT_READ/WRITE returns without a busy retry. Before successful negotiation, no application data permitted. TLS read/write at most one library call, application size bounded to PPBS OfferSize; a pending write must be retried with identical pointer/length and no interleaved read. Any unexpected return/EOF, invalid size, admission loss or clock regression fails closed. Mbed TLS may do multiple BIO calls or expensive crypto internally: this is not a measured CPU/scheduler bound. Certificate creation, cryptographic negotiation, TLS buffers and NVS operations must not run on an active-race critical path. Dedicated resource and scheduling measurements are mandatory; existing XIP 10 sockets remain unchanged, not adequate for production simultaneous capacity. No resource approval inferred.

Release socket, TLS context/config, private key and certificate on completion/failure/destruction; temporary certificate buffers wiped through provider, library handles its internal secrets. No blocking close-notify or flush loop. A successful TLS write hands ciphertext to TCP, not proof of peer delivery. Close after PPBS Done is deliberately bounded; real delivery loss remains Uncertain according to S3g2e, not a reason to overwrite or automatically revoke a vault. Future owner destroys Exchange before Channel, then creates fresh ordinary PPTH transport from committed vault and persists selector hint only after PPTH. No race commands or replacement in this adapter.

## Evidence and limits

New Linux real TCP test creates two actual Mbed TLS 3.6 channels (not a mocked secure flag), negotiates TLS, executes existing PPBS with mock protected stores, verifies exact one write per vault, closes/reloads and authenticates through real PPTH. Tests negotiation deadline, clock regression, entropy/admission failure, invalid role, denied fd ownership, pre-handshake data, malformed TLS record, admission loss, EOF and oversized write. Cumulative host workflow uses existing Ubuntu 24.04 runner; new Mbed TLS job uses official Debian 13 container and signed distro libmbedtls-dev/libssl-dev packages (prints library version), avoiding unsupported runner change and old Ubuntu 24.04 Mbed TLS 2.x API. Package/environment failures are not product test failures. This does not compile the ESP SDK fork or measure actual radio, certificate generation, flash, heap, stack, scheduler latency or Browser coexistence. Existing signed ESP-IDF build and hardware remain untouched.

Remaining: actual target compile and measured qualification, exclusive admission/listener/owner integration and AP/STA generation, protected storage key provisioning, safe interruption/replacement and locator reconciliation, renderer/status/controls, boot epoch and committed preference revision, approved generated socket/heap/PCB budget, separate builds and real device acceptance. No claim of physical readiness.
